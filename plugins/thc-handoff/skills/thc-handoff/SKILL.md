# THC Handoff: 對話交接與接續

長任務常跨越多個對話。依賴 context 自動壓縮會遺失關鍵的技術細節；較可靠的做法是趁 context 仍完整時寫下交接檔，再於新對話中載入。

| 模式 | 觸發 | 動作 |
| --- | --- | --- |
| 存檔模式 | 「存交接檔」、"save this conversation"，或使用者接受主動建議 | 寫入 `HANDOFF.md` |
| 接手模式 | 「從交接檔接手」、"resume from the handoff"，或新對話指向先前的工作 | 讀取、求證、回報後等待確認 |

## 內建寫作規範

本技能的產出 (含 `HANDOFF.md`) 與對話回應都遵循以下規範。若環境已安裝 `thc-zhtw-style`，以其完整規範為準。

- 語氣：正式、中性、精簡，一句一概念；不使用口語、情緒化或行銷式修辭。表格與清單允許短語體。
- 事實與推論分開：優先陳述可驗證的事實與觀察；推論標示「可能」「推測原因」或「建議確認」；避免「一定」「絕對」「完全沒有問題」等絕對語氣。
- 用字：使用台灣繁體中文與台灣資訊產業慣用語，例如程式、資料、預設、伺服器、最佳化。
- 識別字：指令、路徑、檔名、參數、分支名稱一律以反引號標記，逐字保留。
- 標點：中文句讀用全形 `，。、；：「」`；問號、驚嘆號與夾注括號用半形，左右括號必須同為半形；冒號前一個字元不是中文字時用半形 `: `；中文與英文、數字之間加一個半形空格。
- 禁用符號：`→`、`—`、`…`、`～`、`✓` 等特殊符號，改用 `->`、「至」、冒號或逗號分句、`...`、「是」「否」。
- 讀者：技術內容須讓工程師可理解、客戶可接受。
- 風險與推論的呈現：「已知陷阱與失敗的嘗試」與「待解問題與阻礙」中涉及風險或推論的條目，依序寫出觀察、影響與風險、建議行動三段。純事實的段落維持精簡，不為套用結構而增加篇幅。

## 存檔模式：寫入交接檔

交接檔寫在專案根目錄的 `HANDOFF.md`，也就是目前工作目錄所在 git 儲存庫的根目錄；不在 git 儲存庫內時改用目前工作目錄。固定只有一份檔案，每次覆寫為最新版。`HANDOFF.md` 納入 git 追蹤，歷次版本由 git 歷史保存。

### 步驟 1: 檢查既有檔案

| 情況 | 處理 |
| --- | --- |
| `HANDOFF.md` 不存在 | 直接建立 |
| 主題與本次相同 | 直接覆寫 |
| 主題不同，且有未提交的修改 | 告知使用者既有交接檔的主題與最後更新時間，說明覆寫將遺失其內容，等待使用者決定先提交、合併或直接覆寫 |
| 主題不同，但已提交 | 可以覆寫，回報時說明舊版可由 git 歷史取回 |

`git status --short HANDOFF.md` 有輸出，即代表有未提交的修改。

### 步驟 2: 取得時間與版本資訊

以實際指令取得，不得憑推測填寫：

```bash
date '+%Y-%m-%d %H:%M %Z'
git branch --show-current
git rev-parse --short HEAD
```

### 步驟 3: 依範本撰寫

目標是指南針，不是長篇報告：控制在 150 行以內。某段確實沒有內容才略過；精簡的交接檔優於冗長的版本。

```markdown
# 交接：<一句話主題>

> 最後更新：<YYYY-MM-DD HH:MM TZ>，分支：`<branch>`，基準 commit: `<short hash>`

## 目標
<1 至 2 句：最終要達成什麼。>

## 目前狀態
<哪些可運作、哪些壞掉或進行中，具體陳述。>

## 已完成
- [x] <已完成項目>

## 下一步
1. <明確的下一個動作：是任務，不是模糊的意圖。>

## 決策與理由
| 決策 | 理由 |
| --- | --- |
| <做出的選擇> | <原因：最有價值、也最常被省略的欄位> |

## 關鍵檔案與路徑
| 路徑 | 用途或變更內容 |
| --- | --- |
| `path/to/file` | <為何重要> |

## 已知陷阱與失敗的嘗試
- <行不通的做法>：<原因，避免下個對話重蹈覆轍>

## 待解問題與阻礙
- <未解的問題或外部阻礙>

## 如何接續
1. <第一個要執行的明確指令，例如 `uv run pytest -q`>
   - 預期結果：<具體的預期輸出，而非「確認可運作」>
   - 副作用：<無，或說明會改動什麼>
```

好的交接檔具備以下特質：

| 原則 | 原因 |
| --- | --- |
| 記下「為什麼」，不只是「做了什麼」 | 「改用 PyAV」對下個對話沒有幫助；「環境不允許安裝系統 ffmpeg，所以改用 PyAV」能讓下個對話遵守該限制，而非重新爭論 |
| 寫出明確的路徑與指令 | 「修好了 auth 的錯誤」會迫使下個對話重新搜尋；「`src/auth/login.py:42` 的權杖 TTL 檢查」才能直接接續 |
| 記錄失敗的嘗試 | 失敗的嘗試往往是最昂貴的知識；缺少這段，下個對話會再花同樣的時間 |
| 蒸餾，不貼逐字稿 | 整段貼上會重現原本想擺脫的 context 膨脹問題 |
| 標明接續指令的副作用 | 接手時可依此判斷哪些指令能直接執行、哪些須先確認 |

### 步驟 4: 回報

告知使用者檔案路徑與最後更新時間，並說明開新對話後說「從交接檔接手」或輸入 `@HANDOFF.md` 即可接續。是否將交接檔與其他變更一起 commit 由使用者決定，本技能不自行 commit。

## 接手模式：從交接檔接手

1. 讀取 `HANDOFF.md`。檔案不存在時明確告知，並詢問是否在沒有交接檔的情況下繼續，不得臆測其內容。
2. 以實況求證。交接檔寫成後，專案可能已有變動，例如新增檔案、切換分支、測試由失敗轉為通過。
   - 執行 `git status` 與 `git log --oneline -5`，確認交接檔引用的檔案與分支仍存在。
   - 執行 `git log --oneline <基準 commit>..HEAD`，列出交接後的新 commit，判斷交接檔可能過時的部分。
   - 「如何接續」的指令中，唯讀或無副作用者，例如測試、`git status`、lint，可以直接執行以取得實際結果；具副作用者，例如 migration、部署、刪除檔案、寫入外部服務，不得自行執行，列入回報等待使用者確認。
3. 簡要彙整給使用者：目標、交接檔的最後更新時間、目前實際進度，以及交接檔與專案實況之間的落差。例如「交接檔記載測試失敗，目前已通過，可能已修正」。主動指出落差，不沿用過時的假設。
4. 人工確認點：列出依求證結果調整後的下一步建議，使用者明確同意後才開始執行。

## 範例

**存檔**

- 輸入：「下班了，幫我把目前進度存成交接檔，明天接著做。」
- 動作：檢查既有的 `HANDOFF.md`，以 `date` 取得時間，依對話內容填寫範本並覆寫，控制在 150 行以內。
- 回報：「已存到 `HANDOFF.md`，最後更新時間為 2026-11-10 18:05 CST。下個對話說『從交接檔接手』即可接續。」

**接手**

- 輸入：「從交接檔接手，繼續做。」
- 動作：讀取 `HANDOFF.md`，執行 `git status`，比對基準 commit 之後的變動，執行無副作用的接續指令。
- 回報：目標、最後更新時間、實際狀態與落差，列出建議的下一步並等待確認。

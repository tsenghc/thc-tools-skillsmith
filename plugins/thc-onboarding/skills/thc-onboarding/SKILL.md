# THC Onboarding: 動手前先掌握專案

新對話中的 agent 對專案一無所知，貿然實作的風險很高。本技能在動手前自行從專案補齊先決知識，以繁體中文回報，然後停下等待使用者指示。

- 唯讀探查：過程中不修改檔案、不 commit、不執行具副作用的指令。
- 與 `thc-handoff` 的分工：開始前先檢查專案根目錄是否有 `HANDOFF.md`。檔案存在且使用者要接續先前的工作時，停下並建議改用 `thc-handoff` 接手；使用者仍要求完整探查時才繼續。探查過程不讀取 `HANDOFF.md` 的內容，一律由專案本身重建理解。

## 內建寫作規範

本技能的產出 (含專案概況) 與對話回應都遵循以下規範。若環境已安裝 `thc-zhtw-style`，以其完整規範為準。

- 語氣：正式、中性、精簡，一句一概念；不使用口語、情緒化或行銷式修辭。表格與清單允許短語體。
- 事實與推論分開：優先陳述可驗證的事實與觀察；推論標示「可能」「推測原因」或「建議確認」；避免「一定」「絕對」「完全沒有問題」等絕對語氣。
- 用字：使用台灣繁體中文與台灣資訊產業慣用語，例如程式、資料、預設、伺服器、最佳化。
- 識別字：指令、路徑、檔名、參數、分支名稱一律以反引號標記，逐字保留。
- 標點：中文句讀用全形 `，。、；：「」`；問號、驚嘆號與夾注括號用半形，左右括號必須同為半形；冒號前一個字元不是中文字時用半形 `: `；中文與英文、數字之間加一個半形空格。
- 禁用符號：`→`、`—`、`…`、`～`、`✓` 等特殊符號，改用 `->`、「至」、冒號或逗號分句、`...`、「是」「否」。
- 讀者：技術內容須讓工程師可理解、客戶可接受。
- 風險與推論的呈現：「限制與規範」與「未知與待確認」中涉及風險、影響或推論的條目，依序寫出觀察、影響與風險、建議行動三段。純事實的段落維持精簡，不為套用結構而增加篇幅。

## 步驟 0: 盤點可用工具

探查前先確認環境中有哪些工具，優先使用高階工具：

| 工具類型 | 用途 |
| --- | --- |
| 程式碼知識圖譜或索引型 MCP，例如 codegraph | 查詢定義位置、呼叫關係、變更影響範圍與特定區域的脈絡，一兩次呼叫即可取得結構 |
| LSP 或符號工具 | 查詢定義、參照與型別 |
| 專案專屬或 MCP 提供的搜尋工具 | 依工具說明使用 |
| `grep`、檔案讀取、`git` | 以上皆無時的基本手段 |

原則：先盤點再選工具。同一問題有高階工具可用時，不以 `grep` 大量掃描。

## 步驟 1: 唯讀探查

以下查詢彼此獨立，盡量在同一輪並行執行。依專案大小調整深度：小型專案可以全讀；大型專案抽樣關鍵檔案與目錄，並在專案概況中註明未涵蓋的範圍。

### 1a. 專案架構

- 根目錄結構與主要子目錄，例如執行 `git ls-files`、列出頂層目錄。
- `README*`、`docs/` 與架構說明文件。
- 套件與建置宣告檔：`package.json`、`pyproject.toml`、`go.mod`、`Cargo.toml`、`pom.xml` 等。
- 進入點與核心模組，例如 `main`、`index`、`app`、`cmd/`。
- 若有 `CLAUDE.md`、`AGENTS.md`、`.cursorrules`，必須讀取，並視為最高優先的指示。

### 1b. 限制與規範

這是最重要、也最常被忽略的一類資訊。

- `CLAUDE.md`、`CONTRIBUTING*`、`CODE_OF_CONDUCT*`、`SECURITY*`、`LICENSE*`。
- commit 規範：`.cz.toml`、`commitlint.config.*`、`.commitlintrc*`、`.gitmessage`。
- 邊界與禁止事項：環境限制、不可修改的目錄、機敏資料、外部相依限制。
- 明確整理出「不可以做的事」。

### 1c. 開發風格

- linter 與 formatter 設定：`ruff.toml`、`.ruff.toml`、`.eslintrc*`、`.prettierrc*`、`.editorconfig`、`pyproject.toml` 的 `[tool.*]`、`rustfmt.toml`。
- 抽樣 2 至 3 個既有原始碼檔，觀察命名、註解密度、慣用寫法與測試風格。

### 1d. 待辦與未竟事項

- 程式碼中的 `TODO`、`FIXME`、`HACK`、`XXX` 標記。
- `TODO.md`、`ROADMAP*`、issue 連結與文件中的待辦。
- 失敗或被略過的測試，僅在能安全得知時納入。

### 1e. git 紀錄與目前進度

- `git status --short`: 工作目錄是否乾淨、有無未追蹤的檔案。
- `git log --oneline -15` 與 `git branch --show-current`。
- 由近期 commit 推斷進行中的工作與 commit message 慣例。

### 1f. 開發流程

- `Makefile`、`package.json` 與 `pyproject.toml` 的 scripts、`Taskfile`、`justfile`。
- CI 設定：`.github/workflows/`、`.gitlab-ci.yml`，可反映正式的驗收方式。
- `pre-commit` 設定、git hooks 與容器化設定，例如 `Dockerfile`、`compose.yaml`。

## 步驟 2: 呈現專案概況

目標是指南針，不是長篇報告：精簡、易於掃讀，建議 120 行以內。專案確實沒有某段資訊時略過該段，並在「未知與待確認」中註明。

```markdown
# 專案概況：<專案名稱>

## 一句話概覽
<專案用途、技術棧、目前階段>

## 架構重點
- <主要目錄或模組與職責，進入點位置>

## 開發流程
- 安裝：<指令>；建置：<指令>；測試：<指令>；執行：<指令>
- 驗收標準：<CI 執行的項目、必須通過的檢查>

## 限制與規範
- <commit 規範、lint、機敏資料限制、不可以做的事>

## 開發風格
- <觀察到的命名、結構與測試慣例>

## 目前進度
- 分支：`<name>`；工作目錄：<乾淨，或有未提交的變更>
- 近期動向：<由 git log 歸納的進行中工作>

## 待辦與未竟事項
- <TODO 與 FIXME、失敗的測試、文件中的待辦>

## 未知與待確認
- <未涵蓋的範圍、需要使用者釐清的問題>
```

## 步驟 3: 停下等待指示 (人工確認點)

呈現專案概況後停下，不主動實作。可以附上 1 至 3 個建議釐清的問題；是否動工、要做什麼，一律等待使用者明確指示。

## 重要規則

- 必須遵循本技能的內建寫作規範，專案概況與對話回應皆適用。
- 善用工具：先盤點高階工具，沒有時才改用 `grep` 與檔案讀取。
- 遇到阻礙即停下詢問：工具或指令失敗、權限不足、專案結構不明、資訊互相矛盾且無法自行判斷時，停下詢問使用者，不硬猜也不自行繞過。
- 唯讀：探查期間禁止修改檔案、執行 `git add` 或 `git commit`，以及執行具副作用的指令。
- 求證不臆測：以專案實況為準；文件與程式碼衝突時，明確指出落差。
- 蒸餾不傾倒：不貼大段原文或完整的 git log，濃縮成可行動的重點。
- 誠實標示落差：大型專案採抽樣時，說明哪些範圍未涵蓋。
- 專案概況必須使用繁體中文。
- 呈現專案概況後停下，等待使用者指示後才開始任何實作。

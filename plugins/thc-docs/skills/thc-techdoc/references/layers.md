# 分層結構與寫作文法

本文件定義 `thc-techdoc` 階段二的產出規範：分層結構、主體層文法、寫作文法、行內標籤、檢索要求、載體規範與素材處理原則。

## 不變核心四層 (必須具備)

| 層 | 名稱 | 內容 |
| --- | --- | --- |
| L1 | 識別層 | 文件資訊表，含版本、日期、適用範圍、目標讀者、讀者前置知識、前置相依項目、維護者角色、複查週期。另附版本異動表 |
| L2 | 決策層 | 關鍵決策摘要表，欄位為決策項、結論、原因、被否決方案、決策日期、首次版本。本文件若在解決既有問題，前置一節問題分析，欄位為問題類型、具體表現、造成影響 |
| L4 | 主體層 | 依判定的主體型態撰寫，文法見「主體層文法」 |
| L7 | 誠實層 | 已知問題表，欄位為編號、現象、原因、解決、狀態。另附待辦表含優先級，以及後續擴充路線圖 |

## 條件層 (依文件型態啟用)

| 層 | 名稱 | 內容 |
| --- | --- | --- |
| L3 | 全景層 | 一張 mermaid 圖，加實體清單表，加推進順序總表 |
| L5 | 驗證層 | 驗收標準表，加可重複執行的整體檢查程序，加端到端情境測試 |
| L6 | 持續層 | 相依關係圖、日常速查、變更升級流程、不可違反的操作鐵律 |
| L8 | 索引層 | 版本清單、對外介面清單、產出檔案清單、中英對照術語表、存取與憑證索引、已解決問題歷史、決策歷史、參考來源 |

啟用表：

| 文件型態 | L3 | L5 | L6 | L8 |
| --- | --- | --- | --- | --- |
| 建置部署遷移 | 必須 | 必須 | 必須 | 必須 |
| 規範標準字典 | 必須 | 必須 | 可以 | 必須 |
| 維運 SOP 與排錯 | 可以 | 必須 | 必須 | 必須 |
| 設計說明與選型 | 必須 | 可以 | 可以 | 必須 |
| 事後檢討報告 | 可以 | 可以 | 必須 | 可以 |

輸出順序固定為 L1、L2、L3、L4、L5、L6、L7、L8。決策層必須在主體層之前，不得調換。

## 主體層文法 (依判定型態選用，全文必須一致不混用)

| 型態 | 單位 | 每個單位必備 |
| --- | --- | --- |
| 程序型 | 步驟 | 適用對象、前置條件、可直接執行的操作、預期結果、失敗時的徵狀 |
| 定義型 | 條目 | 名稱、語義、約束條件、正例、反例 |
| 論述型 | 主張 | 主張、支持證據、成立邊界、已知的反對意見 |

## 七條寫作文法 (強度為「應該」，允許標註例外)

- G1 三欄理由律：任何選擇寫成選項、結論、原因三欄。不只給結論。原因不得同義反覆，例如「因為比較好」不成立。
- G2 現象三段律：任何問題寫成現象、原因、解決三段。原因欄不得留空或寫不明，必須指向可推理的機制。
- G3 動作與預期成對律：每個操作緊接可觀測的預期結果。無法驗證者標示為無驗證手段。
- G4 對象前置律：每個區塊開頭以下列定式標注。

  ```markdown
  > 適用對象：**[實體]**
  > 前置條件：[必須已完成者]
  ```

- G5 標記分級律：使用下方封閉標籤集，全文語義一致。
- G6 新舊對照律：涉及變更或遷移時，附舊、新、變更說明三欄映射表。
- G7 預留註解律：未來擴充點就地以註解預留在對應位置，並在正文說明啟用方式。

偏離任一條時，必須以下列定式就地標註，且必須寫原因。未附原因的例外視同違反。

```markdown
> **例外：本節不適用 G1。**
> 原因：本節為單一強制規格，不存在被否決的替代方案。
```

## 行內標籤封閉集 (僅此七個標籤，不得自創)

| 標籤 | 語義 |
| --- | --- |
| 【重要】 | 危險與不可逆：破壞性操作、不可逆變更、有時間成本 |
| 【注意】 | 經驗與易錯：易錯點、與直覺相反、非顯而易見的前提 |
| 【必要】 | 欄位或步驟必填：標示某欄位、參數或步驟不可省略 |
| 【實測】 | 已驗證：實際執行過並取得結果的內容 |
| 【暫譯】 | 譯法未確認 |
| 【待辦】 | 未完成事項 |
| 【正式環境】 | 僅適用於正式環境的操作或參數 |

- 密度規則：每句至多一個標籤。區塊標題已表達同一語意時不逐項重複。
- 整段警示改用 blockquote 加粗體，與標籤擇一，不疊用。
- 驗收條件用核取方塊或行首寫驗收。優先級在表格欄位填高、中、低。
- 規範強度用句中的「必須」、「應該」、「可以」，不做成標籤。
- 不使用圖形符號作為標記。

## 供 AI 檢索的額外要求

- 每節開頭必須寫一句自我完備的摘要句，說明本節是什麼、對誰、結論為何。
- 節內不使用跨節指涉，例如「如上所述」、「它」、「同前」。
- 每個 H2 或 H3 節應該控制在約 200 至 800 tokens。
- 不使用 YAML front matter。中繼資料另以 sidecar 檔提供，檔名與格式於階段一確認。
- mermaid 圖旁必須並存文字階層清單。
- 憑證、金鑰、密碼絕不入文，僅在 L8 索引取得途徑。

## 載體規範

- 輸出 Markdown 單一檔案。
- 圖表用 mermaid，寫在標註 mermaid 的 fenced code block 內。
- 無法以 mermaid 表達時退化為縮排文字階層清單，不使用字元繪圖。
- 目錄用相對標題錨點，不手寫已編碼的連結。
- 表格不使用合併儲存格，不在儲存格內換行。單一表格超過約 1000 tokens 時應該拆節。
- 程式碼區塊一律標註語言。

## 風格要求

- 表格優先：能結構化的用表格，散文只做銜接。
- 決策留痕：每個非顯而易見的選擇都記錄取捨與被否決方案。
- 可執行：操作內容可直接使用，不留無提示的預留位置 (placeholder)。
- 缺陷不隱藏：素材中的失敗、繞道、暫時方案，全部進已知問題表或待辦表。
- 不粉飾：不確定處標為待確認，不用模糊語句掩蓋。

## 素材處理原則

- 素材中的失敗嘗試與錯誤訊息是高價值內容，不得當雜訊刪除，必須轉入已知問題表。
- 素材中的口語推理，還原成決策層的原因欄。
- 素材不足時提問，不憑推測補寫。
- 素材出現真實憑證或機密時必須以預留位置替代，僅在索引層記錄取得途徑。
